# Administrator provisioning and password rotation

Status: Implementation under review. Creating or changing an account
requires authorization for the intended environment.

## Purpose

Use the existing admin:set-password command to create an administrator
or change the password of an administrator with the same normalized email.

Administrator provisioning is separate from migrations and content seeding.
It does not create homepage records or sample posts.

Do not add this command to application startup, ordinary builds,
or automatic CI runs.

## Prerequisites

- Confirm the intended database and environment.
- Apply the reviewed migrations first.
- Confirm that the AdminUser and session tables exist.
- Use the reviewed application revision and generated Prisma Client.
- Provide the normal application configuration required by that environment.
- Obtain authorization for the account operation.

The script imports application configuration. In production, its
environment must satisfy production configuration validation, including
the site origin and R2 settings.

The application database URL can be loaded through dotenv.
A developer's local .env must not determine a production operation.

## Credentials

Supply ADMIN_EMAIL and ADMIN_PASSWORD through a trusted one-off job's
secret configuration or another approved process-scoped mechanism.

Use a long, unique password generated by a password manager.
The current validator requires a minimum length of 12 and permits
at most 72 UTF-8 bytes.

Do not store passwords in source files, documentation, issue comments,
command arguments, or literal shell commands saved in history.

Do not print passwords, hashes, connection strings, or the environment.
Keep verbose database debug logging disabled.

Confirm the email carefully:

- Surrounding whitespace is removed.
- The email is converted to lowercase.
- A matching email updates that administrator's password.
- A different email creates another administrator; it does not rename one.

## Authorized operation

After the prerequisites and authorization are satisfied, run:

```text
npm run admin:set-password
```

The script:

1. Validates the supplied credentials.
2. Hashes the password using bcrypt with cost 12.
3. Creates or updates the administrator and deletes all sessions
   in one database transaction.
4. Reports success after the transaction completes.
5. Attempts Prisma and pool cleanup independently.

All sessions are deleted, including sessions belonging to other
administrators and current login forms.

Existing protected requests also validate the administrator's
updatedAt-based session version on subsequent requests.

## Results and failures

Invalid credentials produce fixed guidance and a failing exit status.

Unexpected operation errors report an error ID and an approved
diagnostic code without logging raw error details.

A cleanup error can occur after the credential transaction committed.
A connection failure during commit can also leave the caller uncertain
about the outcome.

Inspect the reported event and verify the account state before deciding
whether another password update is appropriate. Do not assume every
failing process exit means the credentials remained unchanged.

## Verification during an authorized staging rehearsal

- Create a staging administrator and verify login.
- Rotate that account's password.
- Verify that the previous password is rejected.
- Verify that the new password works.
- Verify that an existing administrator session loses access.
- Confirm that editorial content remains unchanged.
- Confirm that the command exits after resource cleanup.
- Confirm that logs contain no credential material.

These checks change staging account and session records and require
authorization before execution.

## After the operation

Remove any temporary ADMIN_EMAIL and ADMIN_PASSWORD settings that were
added to persistent hosting configuration.

Store the credential in the approved password manager.
Record the environment, application revision, result, and any error ID
without recording the password or hash.

Content initialization and production launch remain separate operations.
